# 设计说明：三个选择与它们的代价

这份文档回答「为什么这样做」，不解释「怎么做」。实现细节在 `PROJECT_LAYOUT.md`，逐轮的
取舍与返工在 `LEARNING_LOG.md`。

读完这份，应该能回答三个问题：为什么不用「存状态」、为什么不用「检查锁」、为什么不用
ReAct。以及，为这些选择付出了什么。

---

## 一、为什么是事件日志，而不是存「当前状态」

最直觉的做法是存一份状态：`{余额, 走到第几步, 每步结果}`，每执行完一次就覆盖写。

它有一个致命的空白：**工具已经执行、状态还没写**的那一瞬间。

```
写状态 ──→ 调用工具 ──→ 写状态
              ↑
        进程在这里死了，没人知道钱转了没有
```

恢复时读到的状态是「没转」，但现实可能已经转了。这不是概率问题，是必然会发生的问题——
只要进程会死、网络会断、机器会断电。

事件日志的做法是**先记意图，再动手**：

```
STEP_DECIDED（打算调用什么）
STEP_STARTED（已经交给外部世界了）   ← 过了这条线，副作用可能已发生
STEP_COMPLETED / STEP_FAILED / STEP_UNCERTAIN
```

第二条事件落盘之后才真正调用工具。于是「日志里有意图没有结果」这件事本身，就是一条
精确的事实：**可能已经改了，也可能没有。** 这个状态叫 `UNCERTAIN`，它不能被自动重做，
只能去外部找证据（对账）或问人（复核）。

关键是：视图不是独立存储的，它永远等于日志的折叠结果。

```
RunView = replay(events)
```

所以不存在「状态与日志不一致」这种 bug——它们在定义上就是同一个东西。

**代价**：每次要状态都得重放全部事件；事件表会一直长；读取成了热路径（引擎每一步都读
一遍）。这些都在债务表里。

---

## 二、为什么是栅栏（epoch），而不是「检查一下锁还在不在」

租约解决的是「同一时刻只有一个写入者」。但租约本身会失效：

- 进程被 GC 或调度暂停，醒来时租约已经过期
- 网络分区，持有者不知道自己已经失去它
- 机器休眠，`expires_at` 是墙上时钟

所以「我手上的租约还没过期」这句话，在检查与写入之间就可能变成假的。

本项目的做法是给租约加一个**单调代数**：

```
每次接管，epoch + 1
每次写入，带上你拿到租约时的 epoch
日志在写入事务里比对 runs.epoch
```

比对发生在 `BEGIN IMMEDIATE` 事务内，与「分配 seq」是同一件事。窗口被压进事务，而事务
本身就是原子的。

于是分工很清楚：

- **租约是优化**：它让冲突变少，让双方不必每次都撞车
- **栅栏是正确性**：撞车时由 epoch 决定谁赢，输的那个拿到 `LeaseLost`

两个细节值得记：

- 同一 owner 重复 `acquire` **不**加 epoch。否则每次重启都会把自己的旧写入判成过期。
- 接管只发生在租约过期时。过期不等于对方停了——它可能只是慢。所以接管者进来之后仍然
  可能有两个进程在跑，只是只有一个能写。

**代价**：每次写入多一次数据库往返；每个 worker 都得处理 `LOST`；租约 TTL 依赖本机时钟，
跨机器不可比。

## 三、为什么不 ReAct

ReAct 的形态是：想一步、做一步、看结果、再想。思考与行动在同一个循环里，中间态不落盘。

它能跑通演示，但它回答不了本项目最关心的那个问题：**这次调用到底生效了没有？**
因为「想了什么」只存在于进程内存里，进程一死就没了。

本项目的结构是分离的：

```
policy.decide(view) -> Action      只读视图，返回动作，不碰外部世界
engine                             负责顺序、落盘、调用工具、决定何时停
```

三条由此推出的性质：

1. **同一视图 → 同一份提示。** 提示只由视图与工具清单渲染，不含时间、进程、随机数。
   续跑才有意义——恢复后的视图必然渲染出同一份提示。
2. **决策失败零副作用。** 策略抛错时一个工具都没调用，可以断言「外部世界没变」。
   所以它写 `DECISION_FAILED`（可重试）或 `RUN_FAILED`（确定性），而不是 `UNCERTAIN`。
3. **工具失败要分类。** 确定失败、确定成功、无法确认——三者的后续动作完全不同。
   引擎不猜，只按 `run_tool` 的判定追加事件。

**代价**：模型看不到「自己刚才想了什么」——除非那点想法被写成了事件。这意味着连续推理
能力受限，每一步都要一次完整的模型调用，慢且贵。

**为什么不折中**：把 ReAct 的中间思考也落盘？那就已经是事件日志了，只是事件类型换了个
名字。这个折中等于重新发明一遍，还少了对「副作用是否生效」的建模。

---

## 四、这些选择共同的代价

| 选择 | 换来了 | 付出了 |
|---|---|---|
| 事件日志 | 崩溃可恢复、副作用可审计、视图不会说谎 | 读放大、存储增长、每次状态都要重放 |
| 栅栏 + 租约 | 多 worker 下只有一个能写，且能证明是谁 | 每次写入多一次往返；每个 worker 都要处理 `LOST` |
| 决策与执行分离 | 可续跑、零副作用、失败可分类 | 每步一次模型调用；模型看不到自己的中间想法 |

还有一条贯穿全项目的边界：**日志能自证「记录没被改」，不能自证「记录的是真的」。**
哈希链保护的是前者。要后者，只能靠日志之外的证据源。

---

## 五、明确不做什么

- 不做通用 agent 框架。它只服务一个场景：**有副作用的工具调用 + 必须可恢复**。
- 不做多 agent 协作。协调成本会盖过这个项目真正要证明的东西。
- 不引入向量库或 RAG。决策依据是结构化的视图，不是文本检索。
- 不做「自动重试到成功」。重试必须有确定性依据，否则就是在赌非幂等调用没生效。
- 不为了跑通而放宽协议。解析失败就报错，不接受「大概能看懂」的输出。
